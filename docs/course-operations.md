# 부추 강의 운영 안내

현재 강의 기능은 로컬 PostgreSQL과 Flyway를 사용하는 개발 구현입니다. 초기 강의 6개는 구매할 수 없는 기획 예시이며 **결제는 기본 비활성화**입니다. 실제 Toss 상점 키를 이용한 결제·환불·웹훅 전체 연동은 검증하지 않았습니다.

## 환경변수와 결제 연결

`npm run dev:backend`는 `backend/.env`를 읽습니다. 이미 실행 환경에 주입한 값이 파일보다 우선하며, 변경 후 백엔드를 재시작해야 합니다. 직접 Gradle 또는 IDE로 실행할 때는 같은 값을 실행 환경에 넣습니다.

| 환경변수 | 용도 |
| --- | --- |
| `COURSE_PAYMENTS_ENABLED` | `false`가 기본값. 새 주문·결제 승인 기능을 켤 때 `true` |
| `TOSS_CLIENT_KEY` | 연결할 Toss 결제위젯 클라이언트 키. 결제가 켜졌을 때 프런트엔드에 제공 |
| `TOSS_SECRET_KEY` | 같은 상점·같은 테스트/라이브 환경의 서버 시크릿 키. 브라우저에 전달하지 않음 |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | 기존 로컬 PostgreSQL 연결 설정 |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | 관리자 로그인 설정 |
| `PORT` | 백엔드 포트. 현재 기본값 `8082` |
| `SESSION_COOKIE_SECURE` | HTTPS 운영 환경에서는 `true` |

프런트엔드 API 연결 주소를 바꿀 때는 `frontend/.env.local`의 `BACKEND_URL`을 설정합니다. 시크릿 키를 `NEXT_PUBLIC_*` 변수, 소스 코드, 브라우저 저장소나 문서에 넣지 마세요.

```dotenv
# backend/.env — 실제 값은 운영자가 별도로 주입합니다.
COURSE_PAYMENTS_ENABLED=false
TOSS_CLIENT_KEY=
TOSS_SECRET_KEY=
```

결제 연결 순서는 다음과 같습니다.

1. 사용할 Toss 상점에서 결제위젯용 클라이언트 키와 서버 시크릿 키를 확인합니다. 테스트 키와 라이브 키를 혼용하지 않습니다.
2. 결제위젯의 결제 UI variant를 `DEFAULT`, 약관 UI variant를 `AGREEMENT`로 준비합니다. 현재 구현은 이 두 값을 사용하므로 다른 variant를 쓴다면 프런트엔드 설정도 함께 바꿔야 합니다.
3. **가상계좌는 결제위젯의 제공 수단에서 제외합니다.** 현재 구현은 즉시 승인된 `DONE` 상태만 수강 권한으로 인정하며, 프런트엔드에서도 가상계좌 선택을 차단합니다. 입금 대기·입금 통지에 따른 수강 개시는 구현하지 않았습니다.
4. 테스트 환경에 두 키를 주입하고 `COURSE_PAYMENTS_ENABLED=true`로 재시작합니다. `/api/payments/config`가 활성 상태를 반환하는지 확인합니다. 이 응답에는 시크릿 키가 포함되지 않습니다.
5. 공개 HTTPS 주소를 사용할 때 성공·실패 복귀 경로 `/payments/success`, `/payments/fail`과 아래 웹훅 경로가 정상 연결되는지 확인합니다.

구현은 Toss JavaScript SDK v2의 `https://js.tosspayments.com/v2/standard`, 비회원 결제위젯, 서버 결제 승인을 사용합니다. 결제 결과의 URL만 보고 수강을 열지 않으며 서버에서 주문과 금액·통화·결제 키·승인 상태를 확인합니다. SDK의 위젯 렌더링과 성공/실패 복귀 방식은 [Toss 공식 결제위젯 문서](https://docs.tosspayments.com/sdk/v2/js/payment-widget)를 참고하세요. 확인: 2026-10-15.

## 실강의 등록

관리자 `/admin`의 **강의 관리**에서 새 강의를 만들거나 기획 예시를 실제 콘텐츠로 수정합니다.

1. 강의명·주소·분야·난이도·소개와 강사 정보를 작성합니다. 강의 주소는 발행 후 가능하면 유지합니다.
2. 강의료, 수강 기간, 주당 권장 학습 시간과 추가 실습비를 입력합니다. 강의료와 실습비는 구매자가 구분할 수 있게 안내합니다.
3. 완성할 결과물과 준비물을 줄마다 하나씩 작성합니다. 관련 부업이 있다면 부업 주소의 마지막 부분을 연결합니다.
4. 챕터와 수업을 추가하고 순서를 정합니다. 수업에는 일반 텍스트 본문 또는 재생 가능한 영상 주소를 넣습니다. 미리보기 표시를 켠 수업은 누구나 볼 수 있습니다.
5. 실제 환불·취소 안내와 수강 문의 이메일을 등록합니다. 기획 예시를 실제 강의로 전환한다면 **예시 강의** 표시를 해제합니다.
6. 소개·미리보기·수업 내용을 확인한 뒤 판매 상태를 변경합니다. 판매 중 저장 시 필수 조건을 서버가 다시 검증합니다.

| 상태 | 방문자에게 보이는 내용 |
| --- | --- |
| 작성 중 `DRAFT` | 공개 목록·상세에서 비공개 |
| 오픈 예정 `COMING_SOON` | 소개와 지정 미리보기 공개, 구매 불가 |
| 판매 중 `PUBLISHED` | 결제 연결이 활성화되면 개별 구매 가능 |
| 판매 종료 `ARCHIVED` | 공개 목록·상세에서 비공개, 유효한 기존 구매자는 강의실에서 수강 가능 |

판매 중 상태에는 최소 1,000원의 가격, 강사·소개·환불 안내·문의 이메일, 하나 이상의 결과물·준비물과 유효한 수업이 필요합니다. 수업마다 20자 이상의 본문 또는 영상 주소가 있어야 합니다. `isDemo=true`인 강의는 판매할 수 없습니다.

수업 완료 기록은 수업 ID와 연결됩니다. 이미 판매한 강의를 수정할 때 기존 수업을 삭제하고 새로 만들면 이전 완료 기록과 연결되지 않으므로, 기존 수업을 그대로 편집하는 방식을 우선합니다. 내용 변경이 기존 구매자에게도 반영된다는 점을 고려해 검수합니다.

## 이미지와 영상의 현재 범위

강의 대표 이미지는 공개 HTTPS 이미지 주소를 입력합니다. 비워두면 분야별 기본 커버를 보여줍니다. 강의 영상은 HTTPS 영상 파일 URL을 브라우저 플레이어에서 직접 재생하는 방식이며, 임의의 외부 동영상 페이지 주소를 삽입하는 기능은 아닙니다. 수업 본문은 HTML이 아닌 일반 텍스트입니다.

**기업 게재 신청의 프리사인 이미지 업로드와 유료 강의 영상 저장소는 별개입니다.** 현재 강의 관리에는 영상 업로드·변환·CDN 서명 기능이 없습니다. 유료 수업 API에는 구매 권한 검증이 있지만 한 번 제공한 공개 영상 URL의 직접 재생을 회수할 수는 없습니다.

유료 영상을 보호하려면 비공개 원본 저장소와 CDN을 연결하고, 유효한 구매 권한을 확인한 뒤 짧은 만료 시간이 있는 서명 URL 또는 쿠키를 발급하도록 추가 구현해야 합니다. 만료되는 영상 주소를 관리자가 수동으로 고정 입력하는 방식은 시간이 지나면 정상 구매자도 재생하지 못하므로 운영 방식으로 삼지 않습니다. 연결 전까지는 공개되어도 되는 미리보기 자료로 동작을 확인하세요.

## 구매 코드와 고객 응대

구매자는 회원가입 없이 이름·이메일과 동의 정보를 제출합니다. 생성된 주문 번호와 43자의 복구 코드를 현재 브라우저에 저장하고, 별도 보관을 확인한 뒤 결제 화면으로 이동합니다. 다른 기기에서는 `/classroom`에서 두 값을 입력해 주문을 연결합니다.

- 복구 코드는 주문 조회와 수강 권한을 가진 비밀 정보입니다. 로그·URL·공개 문의 게시글에 노출하지 않습니다.
- 서버는 코드의 해시만 저장하므로 관리자가 원문 코드를 조회할 수 없습니다.
- 현재 이메일 검색만으로 주문을 복구하거나 코드를 재발급하는 기능은 없습니다. 부추 자체의 주문 이메일·수강 코드 자동 발송도 포함하지 않습니다.
- 브라우저 데이터를 지우거나 기기를 바꾸면 따로 보관한 주문 번호·코드가 필요합니다. 코드 분실 고객을 위한 본인 확인·재발급 절차는 별도로 설계해야 합니다.

문의에는 주문 번호를 사용하고, 구매자에게 결제 비밀번호나 카드 정보를 요청하지 않습니다. 강의별 공개 문의 이메일은 운영 가능한 주소로 설정합니다.

## 환불과 외부 상태 동기화

관리자의 **강의 주문**에서 결제 완료 주문을 확인하고, 환불 정책과 구매자 요청에 따라 사유를 입력한 뒤 **전액 환불 확정**을 누릅니다. 실제 결제사 취소 결과가 확인되어야 DB 상태를 `CANCELED`로 바꿉니다. 현재 부분 환불 기능은 없습니다.

Toss 웹훅에는 다음 정보를 등록합니다.

| 항목 | 설정 |
| --- | --- |
| 수신 URL | `https://서비스도메인/api/payments/webhook` |
| 이벤트 | `PAYMENT_STATUS_CHANGED` |
| 요청 형식 | `POST`, `application/json` |

등록 위치와 이벤트 종류는 [Toss 공식 웹훅 연결 안내](https://docs.tosspayments.com/guides/v2/webhook)를 참고하세요.

웹훅의 상태·금액을 그대로 신뢰하지 않습니다. 기존 결제 완료 주문의 번호와 결제 키가 일치하면 서버 시크릿 키로 Toss 주문을 다시 조회하고, 확인된 전액 취소만 DB에 반영합니다. 웹훅만으로 미결제 주문을 결제 완료로 바꾸지 않습니다. 중복 전송은 같은 결과로 처리합니다.

웹훅이 늦거나 누락되어도 **강의 정보·수업·진도 저장 요청마다** 결제사를 조회해 주문·결제 키·통화·금액·`DONE` 상태와 잔액을 확인합니다. 전액/부분 취소나 조회 실패 시 새 수업 응답을 제공하지 않습니다. 이미 브라우저에 전달된 내용이나 영상 URL은 회수되지 않습니다.

주문 목록은 DB에 기록된 상태를 표시합니다. 웹훅이 누락되면 목록에는 결제 완료가 남아 있으면서 실제 수강은 차단될 수 있습니다. 이런 문의가 오면 Toss 주문과 웹훅 전달 결과를 확인하고 전액 취소 알림을 다시 처리합니다. 부분 취소는 현재 DB의 별도 상태로 관리하지 않으며, 운영 정책과 후속 구현이 필요합니다.

`COURSE_PAYMENTS_ENABLED=false`로 새 판매를 중단해도 서버 시크릿 키가 남아 있으면 기존 구매자의 결제 조회·수강 확인과 웹훅 조회는 유지됩니다. 시크릿 키를 지우거나 Toss 조회가 중단되면 기존 구매자도 수업을 열 수 없습니다. 관리자 전액 환불도 새 판매 활성 여부와 관계없이 서버 시크릿 키로 진행할 수 있습니다.

## 판매 전 운영 준비와 검증

실서비스 운영 주체에 맞는 사업자·판매자 정보, 서비스 이용약관, 개인정보 처리·보관 안내와 강의별 환불 규정을 확정해 게시해야 합니다. 현재 화면의 기본 안내는 운영자의 최종 약관이나 법적 검토를 대신하지 않습니다. 실제 적용 요건과 PG 심사 조건을 확인하고 필요한 검토를 거친 뒤 라이브 결제를 활성화합니다.

다음 항목은 실제 상점 환경에서 별도로 확인합니다.

- 테스트 키로 카드 등 허용 결제 수단의 성공·실패·사용자 취소와 모바일 복귀.
- 동일 주문 승인 재시도, 새로고침 후 결과 확인, 금액 변경 요청 거절.
- 정상 구매 수강, 잘못된 코드·미결제·만료 주문 접근 거절.
- 관리자 전액 환불, Toss 콘솔 전액 취소와 웹훅 수신, 취소 후 수업 차단.
- 결제사 조회 장애 시 안내와 회복, 기존 구매자가 있는 상태의 판매 중단.
- 실제 영상 파일의 브라우저 재생과 접근 정책, 주문 코드 보관·복구 절차.

현재 자동 검증은 결제사 응답을 대체한 테스트를 포함하며, 실제 PG 상점의 결제 성공이나 정산을 의미하지 않습니다. 실제 강의 자료·상점 키·운영 정책·비공개 영상 저장소 연결은 운영자가 준비해야 합니다.

## 데이터 관리

강의는 Flyway `V4__courses.sql`, 주문·진도는 `V5__course_orders.sql`에서 생성됩니다. 적용된 마이그레이션을 수정하지 말고 스키마 변경은 새 버전으로 추가합니다. 기획 예시는 최초 적용 시에만 들어가며, 관리자에서 저장한 강의 내용은 DB에 유지됩니다. 운영 주문과 수강 기록을 보존할 수 있도록 DB 백업·복원 절차를 준비합니다.

서비스 방향과 현재 기능 범위는 [부업 강의 기획](course-product-plan.md)을 참고하세요.
